<objective>
Deliver named snapshots end-to-end at the library level: the engine orchestration Snapshot (force the current dump to complete, then byte-copy the finished dump under a validated name) and Restore (decode with the same codec, replay each snapshot key as an ordinary fresh-version write or delete so it replicates and wins by normal LWW), plus the adapter's security and error-class hardening.

Purpose: This plan completes PERS-05 and closes Phase 3 — snapshots are the operator-facing recovery primitive; restore-as-writes is what makes a restored state replicate like any other write instead of needing a special replication path (D-09).
Output: Engine.Snapshot and Engine.Restore in internal/app/persist/engine.go, internal/persistfile/snapshot_test.go, engine snapshot/restore tests.
</objective>

  engine.go — func (e *Engine) Snapshot(name string) error: force a completed dump covering all current state, then byte-copy. Flush mechanism: send a reply channel on the flushCh field plan 03-01's Run loop already selects; the dumper runs runDump immediately (bypassing the debounce quiet window — this is the "forces the current dump to complete" of D-10; when not dirty there is nothing unconfirmed, Run replies without dumping) and replies with the dump's error. If the flush errors return it and abort — never snapshot state that is not confirmed on disk. On success return e.dumps.CreateSnapshot(name) directly: the adapter reads the finished main dump and atomically writes the copy (D-10's byte-for-byte copy is adapter-owned; the engine never touches snapshot bytes). Calling CreateSnapshot from the caller's goroutine is safe against a concurrent dump: the adapter's atomic rename means os.ReadFile of main always observes exactly one complete generation (older or newer inode), never a torn one.

  engine.go — func (e *Engine) Restore(name string) error: data, err := e.dumps.ReadSnapshot(name); on error return it (a missing snapshot surfaces the adapter's fs.ErrNotExist-wrapped error — distinguishable, never an empty silent success). records, discarded, err := codec.Decode(data) with the same generation-level error semantics as dump loads; generation-level error returns it; the discarded count is accepted (snapshot records obey the same discard classes). Replay per D-09 as ordinary writes with fresh versions, in deterministic sorted-key order: for each key in slices.Sorted(maps.Keys(records)) — if the record is Deleted, call e.store.Delete(key) and skip on errors.Is(err, storage.ErrNotFound) (missing or already-tombstoned: nothing to beat, Delete writes nothing anyway per store.go lines 179-183) while any other store error returns; if live, call e.store.Set(key, rec.Data) and skip on storage.ErrValueTooLarge (a config-shrunk limit must not abort restore, mirroring Open's skip rule) returning any other error. The replay goes through the STORE's write path — the same fresh-version semantics as an ordinary write, never Merge (the snapshot's own versions are not re-installed; fresh versions are what make the restore replicate and win by normal LWW). After the replay, mark dirty and perform one final flush exactly as Snapshot does, returning its error — the Restore call is itself write-confirmed: it returns nil only after a dump containing every replayed write completed (research Open Question 4 resolved: per-key ordinary-write semantics with batched confirmation — sequential per-write blocking would serialize N writes at one debounce each, ~50ms per key at 10k keys, while the batched flush preserves identical per-key semantics and a stronger per-operation confirmation).

  doc.go: document the two operations' contracts — Snapshot's force-then-copy guarantee (D-10), Restore's replay-only-snapshot-keys rule with absent keys untouched (D-09), fresh-version dominance, the skip rules for tombstone-no-ops and oversized values, and that both operations fail with the underlying error rather than degrading silently.

## Flagged Assumptions (Edge Probe — intentionally unresolved until phase verification)

1. **Restore confirmation batching:** Restore replays each key through the store's ordinary write path (fresh versions, identical per-key semantics) but confirms the whole batch with ONE final flush rather than blocking per write — the reading of D-09 "replay as ordinary writes" as semantics-level, not confirmation-path-level; flagged for the verifier together with plan 03-01's PERS-04 assumption.
2. **Snapshot overwrite policy:** re-creating an existing name atomically overwrites in place with no .prev kept for snapshots (research Open Question 2 resolved) — snapshots are operator-named recovery points, not crash generations; the dump's own .prev chain is the crash mechanism.
