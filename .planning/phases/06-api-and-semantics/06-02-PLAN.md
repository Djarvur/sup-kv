<objective>
Make `wait_for_replication` report exactly what happened: capture the peer-id set immediately before the engine write, carry it through the notification into the core's pending entry and the adapter's tracker, answer zero peers and a nil seam with `(false, 0, 0)` immediately, ignore Acks from peers outside the write-time set, stop the discovery flush from growing the awaited set, and pin the existing `Superseded` fast path with deterministic and real-adapter tests.

Purpose: A-01/IN-05 — the current report is an overstatement (zero peers says acked) and a moving target (peers discovered mid-wait join the wait-set but not the total, producing a false negative at the timeout). The write-time set is the only honest answer.
Output: `ServerOptions.WritePeers`, peer-carrying `LocalNotify`, `Core.PeerIDs`/`PeerGeneration`, an adapter `KnownPeerIDs` mirror, a tracker scoped to its captured set, and the test matrix for zero-peer, unknown-Ack, displaced-version and discovery-flush cases.
</objective>

<assumptions>
Probe rows owned by this plan (specless fallback, unresolved):

- **APIS-01 (concurrency) — what is guaranteed under parallel writes?** Assumption: the handler captures the peer set in one read before the engine call; concurrent writes each capture their own set; a newer write under the same key supersedes the older tracked version and resolves it through `ResultSuperseded`. Resolution: the tracker is per `(key, version)`, `trackLocalWrite` keeps the supersession guards unchanged, and the tracker map is bounded by concurrent waits because every wait path deletes.
- **APIS-01 (boundary) — zero/one peer and one step either side.** Assumption: zero captured peers → `(false,0,0)` and a release call; one captured peer → wait for its Ack; a captured peer that has already left the core peer table → `WaitSetEmpty` (honest false) instead of a timeout; a peer discovered one instant after capture → broadcast but not awaited. Resolution: all four are tests in this plan.
- **Decision fidelity:** D-01 chose the write-time peer set + immediate zero-peer answer + Superseded fast path. No deferred idea is implemented.
</assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → Set/Delete | `wait_for_replication`, `wait_timeout_ms`, and the key/data are untrusted request input. |
| Peer datagrams → Ack handling | Any node can send an Ack for any `(key, version)`; the wait report must not trust a stranger. |
| Handler goroutine → adapter tracker | Cross-goroutine resolution by channel close and per-tracker mutex. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-04 | Spoofing | `Adapter.applyResults` / `tracker` | high | mitigate | The tracker stores `wants` from the write-time slice and counts only member Acks; a stranger Ack cannot increment the count or set `ok`. |
| T-06-05 | Denial of Service | zero-peer wait path | high | mitigate | The handler still calls the seam with `total=0`; `WaitReplicated` deletes the tracker on that path and on every return path; a tracker-map test pins the bound. |
| T-06-06 | Tampering | `Server.Set`/`Delete` peer capture | medium | mitigate | Capture happens once, immediately before the engine call, and the same slice feeds notify and wait; the wait never reads the live table. |
| T-06-07 | Repudiation | discovery flush | medium | mitigate | The flush no longer adds to the promise; the record still reaches the new peer, and the pending wait-set test pins that the promise did not grow. |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan; any dependency added later requires the package-legitimacy gate and a blocking human checkpoint. |
</threat_model>
