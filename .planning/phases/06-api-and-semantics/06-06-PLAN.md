<objective>
Gate the Watch feed on durability: tag every store install with its content generation, publish the generation covered by the last successful dump from the persist engine after `confirmWaiters`, hold events in a bounded hub queue, release them in install order when `gen <= confirmed`, suppress the startup-load tap, and end streams with `Unavailable` on shutdown.

Purpose: A-04 — the tap fires at install, before the dump that makes the record durable, and a shutdown stream ends as OK. The fix is a watermark from the persistence engine, not a handler-side notification (which would lose dump-failed-then-confirmed writes).
Output: `OnChange` generation parameter, `persist.Config.OnConfirmed`, scheduler watermark publication, hub pending/Confirm, loader suppression, Unavailable shutdown, and the exactly-once/dump-failure/startup tests.
</objective>

<assumptions>
Probe rows owned by this plan (specless fallback, unresolved):

- **APIS-04 (concurrency) — what is guaranteed under concurrent writes, dumps, and shutdown?** Assumption: the store's generation is monotone and bumped once per install under the write lock; the scheduler reads it before `Records()` and publishes it only after a successful save and `confirmWaiters`; the hub releases in arrival order, so each install is delivered at most once and in install/version order. A write racing the capture is covered by the next dump. Shutdown closes channels with a fresh Unavailable status; a subscriber sees either a final event or the status, never a silent OK. Resolution: the exactly-once, dump-failed-then-confirmed, ordering, and shutdown tests in this plan.
- **Snapshot asymmetry:** the subscribe snapshot is the current in-memory state (what `Get` sees); the live feed is the durable change feed. This is documented in plan 06-09 and is not a defect.
- **Decision fidelity:** D-04 chose after-dump-confirmation, exactly once, deletions as events, version order, Unavailable shutdown. No deferred idea is implemented.
</assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Store install → Watch hub | The tap runs under the store write lock and must never block. |
| Persist engine → hub watermark | The durable fact crosses from the engine's goroutine to the hub's. |
| Client → Watch stream | Prefix, subscriber lifetime, and slow-reader behavior are untrusted. |
| Startup dump → hub | A loaded dump is not a change feed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-17 | Repudiation | `WatchHub.Ingest`/`Run` | high | mitigate | Events are released only on `gen <= confirmed`; the engine publishes `OnConfirmed` only after `confirmWaiters`; an unconfirmed write is never announced. |
| T-06-18 | Denial of Service | `WatchHub.pending` | high | mitigate | Pending is bounded by `watchIngress`; overflow disconnects all subscribers and clears pending; resubscribe plus snapshot heals. |
| T-06-19 | Spoofing | `shutdownSubscribers` | high | mitigate | Every shutdown close writes a fresh `codes.Unavailable` status; the handler returns it, so a dying node never looks like a clean end of stream. |
| T-06-20 | Denial of Service | `persist.Open` startup tap | medium | mitigate | A synchronous loading guard suppresses the tap around `mergeRecords`; a loaded dump cannot fill the hub queue. |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan; any dependency added later requires the package-legitimacy gate and a blocking human checkpoint. |
</threat_model>
